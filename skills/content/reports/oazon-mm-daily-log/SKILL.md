# 从 Mattermost 生成个人日报

## 目的

把某一天散落在十几二十个 Mattermost 频道里的上千条消息，收敛成一份**本人视角**的工作日报：按项目分组、每条「做了什么 + 关键结论/数据」、末尾带工时、合计约 8h。

流程是**取数 → 归纳 → 出草稿 → 用户确认 → 追加到 `daily.md`**。写入前必须先给 diff review，用户点头才落盘（见步骤 5）。

## 输入

- **日期**：默认按 Asia/Shanghai 的今天；用户说「补 8.11 的」就取那天。
- **本人身份**：默认取浏览器登录态里的 `users/me`（通常是 `loki`），无需询问。
- 前置条件：
  - `opencli` 在 PATH 中，`opencli doctor` 显示 daemon 与 extension 均已连接；
  - 浏览器里 mm.oazon.com **已登录**（脚本会验，401 时需用户手工登录）；
  - `python3`。
- 可选：用户指定只关注某几个项目，或指定合计工时不是 8h。

## 工作流程

### 1. 确认口径

只在用户没说清时问，且一次问完；其余按默认值直接开工：

- 日期（默认今天）
- 范围（默认**只写本人**；用户明确要"全公司/团队维度"时才做汇总视角）
- 合计工时（默认 8h）

不要先出一版全公司汇总再返工——默认就是个人日报。

### 2. 抓取

```bash
python3 scripts/fetch_mm_day.py --out <工作目录> [--date YYYY-MM-DD]
```

工作目录放到会话 scratchpad，不要落在用户项目里。脚本会：

1. `opencli browser mm open https://mm.oazon.com/`（后台窗口）；
2. 验登录态，枚举 team 与频道，按 `last_post_at` 筛出当天活跃频道；
3. 分批翻页拉取当天消息（已处理时区与翻页两个坑，见 `references/mattermost-api.md`）；
4. 落盘。

产物：

| 文件 | 用途 |
|---|---|
| `mine.txt` | **主要输入**。我发的 + @我 的消息，并补全所在 thread（bot 的回答通常不 @ 我） |
| `summary.txt` | 每频道条数与时间区间、发言人排行；用来判断工时分布 |
| `ch-NN-*.txt` | 分频道全文，`mine.txt` 里上下文不够时按需回查 |
| `posts.json` | 结构化全量数据 |
| `meta.json` | 抓取参数、频道清单、统计 |

常用开关：`--date` 补历史、`--batch` 调小以避开 eval 超时、`--truncate 0` 关闭截断、`--no-threads` 只看直接相关。

### 3. 读取与归纳

1. 先读 `summary.txt`，掌握当天频道分布和活跃时段。
2. 读 `mine.txt`。它通常几百条、100KB 上下，**分段读完，不要只读开头就下结论**。
3. 需要补上下文时再打开对应的 `ch-NN-*.txt`。
4. 按当天实际主线归并项目（不套固定项目列表），每条提炼成「做了什么 + 关键结论/数据」。
5. 按消息时间跨度估工时，参考 `references/report-format.md` 的区间表，合计约 8h。

判断哪些算"我的"：我发的指令与提问、我做的拍板与结论、我驱动 bot 完成的工作、指派给我或由我关闭的卡片。别人在频道里自己干的事不算。

### 4. 输出草稿

先在会话里给出草稿，等用户确认。此时可以顺带说明哪些事被有意排除了（别人主导的、你只被 cc 的），让用户有机会捞回来。

### 5. 写入 daily.md

目标文件（Obsidian 库，Windows 侧 `D:\obsidian\xnote\WorkLog\Oazon\daily.md`）：

```
/mnt/d/obsidian/xnote/WorkLog/Oazon/daily.md
```

路径不存在就是库又改名了，用 `find /mnt/d/obsidian -maxdepth 4 -iname daily.md` 定位，别拿 `WorkLog/DigiFinance/daily.md` 那份。

**顺序不能颠倒：先备份 → 生成 diff → 用户确认 → 才写入。** 格式约定与逐条落点见 `references/daily-md.md`。

1. 备份到会话 scratchpad：`cp <target> $SP/daily.backup-$(date +%Y%m%d-%H%M%S).md`；
2. 在 scratchpad 里拼出新文件（`head` + 新块 + `tail`），**不要直接改原文件**；
3. `diff -u` 出改动给用户看，同时汇报工时合计（用 `grep -oE '（[0-9.]+h）' | tr -d '（h）' | paste -sd+ | bc` 验算，必须等于约定值）；
4. 用户确认后再覆盖写入，并回读插入处核对。

用户已经说了「写入」「补到 daily.md」时，不必再问一次要不要写，但**仍要先把 diff 贴出来**——它同时是给用户的最后一道校对。

## 输出要求

格式规范、写作要求、工时区间、完整真实样例和反例，全部见 `references/report-format.md`。要点：

```markdown
- **<项目名>**
    - <一句话说清做了什么 + 结果>（Xh）
- **其他**
    - <零散事项>（Xh）
```

- **项目名用短名**（`SyncSign`、`MOCREO V3`、`CalendarLoop`、`http_server`），不带修饰语、不带时长；归不进去的进 `其他`。
- **每个子条目正文 ≤30 字**（不含卡片 URL 与工时），一条只说一件事。
- 子条目必须带工时，最小单位 0.5h，合计约 8h。
- **说人话**：不写函数名、文件名、参数名、commit hash、卡片 id，翻译成业务说法。
- **但保留数字**：台数、条数、百分比、前后对比是唯一不能删的东西。
- Boost 卡片链接直接套在已有文字上，不为加链接而增字。卡片 URL 在 `mine.txt` 里被脱敏成 `[url]`，**要从 `posts.json` 里捞真链接**（`grep -oE 'https://boost\.oazon\.com/kanban/board/[a-z0-9]+\?card=[a-z0-9]+'`）。
- 会话草稿末尾可附一行「明日待跟进」，但**不写进 `daily.md`**——那个文件里从来没有这种写法，且不计入工时。

先按细节写底稿核对依据，再压成 30 字成稿发出——压的是表达，不是依据。

## 检查项

- `opencli doctor` 通过，`users/me` 返回 200，日期与用户要求一致。
- `summary.txt` 里各频道的时间区间覆盖了正常工作时段。**若最早消息集中在午后、上午一片空白，几乎一定是日界线算错了**，回到 `references/mattermost-api.md` 的「坑 1」核对，不要直接出报告。
- 抓取条数量级合理（该账号平时约 1000–1400 条/天）。明显偏少时核对「坑 2」翻页终止条件。
- `mine.txt` 已完整读完，不是只读了开头。
- 每个条目都带工时，项目名不带工时，逐项相加接近 8h。
- **逐条数过字数，正文都在 30 字以内**；超了的拆成两条或再删修饰。
- **通读一遍没有函数名、文件名、参数名、commit hash**；同时每条至少留下一个能证明结论的数字或结果。
- 项目名是短名，没有修饰语，同一项目没有被拆成多个大项。**优先复用 `daily.md` 里近期用过的项目名**，别为两三个条目新造一个大项。
- 每个条目都能在原始消息里找到依据，没有推测或编造的内容。
- 只包含本人的工作。

写入 `daily.md` 时另加：

- 已备份原文件，且 diff 已经给用户看过。
- 工时用命令验算过，不是目测。
- 缩进是 **4 个空格**、括号是**全角 `（Xh）`**、日期是裸行 `8.20`（照抄文件里既有的写法，不要凭印象）。
- 只新增一个日期块，diff 里没有意外改动到其他行。

## 边界

- **对 Mattermost 只读**。不发消息、不回帖、不改任何内容。
- `daily.md` **只追加当天的新块**，不改写、不重排历史日期块；写前必备份 + 出 diff。
- 用户没确认就不落盘。「整理日报」默认只到草稿为止，除非用户明确说了写入。
- 不把工时凑数——宁可如实给出 6h 并说明当天信息不足，也不要编条目填满 8h。
- 不外传抓取内容：`posts.json` 含内部讨论与客户信息，只留在本地工作目录，不要上传到外部服务、不要贴进公开渠道。
- 不在脚本或文档里保存 token、密码、cookie。
- 用户明确要"全公司维度汇总"时才做团队视角，否则一律个人视角。
